Box Mount 0.6.0 Field Report

Findings from building a multi-agent document-processing demo on Box Mount with the Temporal Agent Harness. Five sandboxes ran concurrently, each with its own box-mount daemon over the same Box folder, and handed files to one another only through Box.

Prepared by Adam Cavaliere, Temporal · Observed 13–15 October 2026 · All log timestamps are UTC on 14 October 2026

Summary

Box Mount did what we needed for the core of the demo. A daemon per sandbox kept a real POSIX directory in two-way sync with Box, with no FUSE or privileged container. Uploads landed in about 1.4 seconds, and a file written in one sandbox typically appeared in another in about 4 seconds. JWT setup was straightforward.

We hit three issues we would rate high. A folder that is deleted and later re-created can be bound to the trashed Box folder in other sandboxes, after which files fail to sync or upload to the wrong place. A near-simultaneous write from two sandboxes started an endless loop of conflict copies. Separately, the sync log records live OAuth access tokens in plain text. Several smaller issues affect restarts, change notifications and the permissions model Box recommends for agent sandboxes. Each has a workaround, which we list.

Findings

#1

Re-created folder bound to the trashed Box folder after inode reuse

High
What happened

Sandbox A deleted Work/INV-20417/, which moved it to the Box trash. Sandbox B applied the delete locally. Later, B created a folder at the same path. ext4 handed it the same inode number as an earlier incarnation of that folder (unix:65025:7563), and the daemon treated it as the trashed Box folder 427439254984.

Creating a subfolder inside it then failed with Not Found. The file written inside that subfolder was uploaded to the root of the mounted Box folder instead. A second variant: a local update to a file whose Box copy had been trashed retried update_remote_file … Not Found indefinitely and never fell back to creating the file.

Evidence

Reproduce
  1. Mount the same Box folder in two sandboxes, A and B.
  2. In B, create X/ and a file inside it. Wait for both to sync.
  3. In A, delete X/. Wait for B to apply the delete (see finding 4).
  4. In B, create X/ again, then X/Y/ and a file inside Y/. On ext4 the inode number is often reused when nothing else has been created in between.
  5. Observe create_remote_folder … Not Found, and the file uploaded to the mount root.
Impact

Agent output is silently misplaced or never uploaded, while the agent's local view looks correct. Any delete, whether from an agent or from a person in the Box web app, can poison a later write in a different sandbox. Downstream agents waiting for the file wait forever.

Workaround

Nothing is deleted in the mount while sandboxes are running, and each run writes to a new, uniquely named folder. Between runs we wipe every sandbox's data and mount volumes, delete old outputs from one fresh sandbox, then start all sandboxes fresh.

Suggested fix

On applying a remote delete, drop the inode-to-Box-ID mapping for the item and its descendants even if the local item can't be resolved. Before reusing a mapping, confirm the inode's identity (for example inode plus creation time or generation number). On Not Found for a parent, re-resolve by path or recreate it rather than falling back to the mount root.

#2

OAuth access token written to sync logs in plain text

High
What happened

The bundled Box SDK logs the full response of POST /oauth2/token at INFO, including the bearer access_token (valid about an hour). It appears in logs/box-mount-sync.stderr.log and in each per-run log, in all five sandboxes, at every token refresh.

Evidence
14:17:43 [boxsdk.network.default_network] INFO: "POST https://api.box.com/oauth2/token" 200 560
{'access_token': '[redacted for this report]',
 'expires_in': 3766,
 'restricted_to': [],
 'token_type': 'bearer'}
Impact

Anyone who can read the log directory can act as the service account until the token expires. Agent platforms commonly ship container logs to central logging, and support often asks for logs. In our setup only the daemon user can read the logs, but not every deployment will separate users.

Suggested fix

Redact token fields (access_token, refresh_token, JWT assertions, client_secret) in SDK network logging, or log request and response bodies only at DEBUG.

#3

Endless conflict-copy loop after a near-simultaneous write from two sandboxes

High
What happened

Two sandboxes mounting the same folder each wrote review_memo.md into the same new folder within milliseconds: one wrote an empty file, the other the full content. That came from our own setup (one agent's two-step save split across two workers), and a conflict copy is the documented outcome.

The receiving daemon did not settle, though. It created review_memo.conflict.local.<timestamp>.md, uploaded it, and then created and uploaded another one every 2–3 seconds: 78 copies in about 4 minutes, each downloaded by every other mount, until we stopped that container. Both sandboxes also appear to have created the new parent folder independently: the two uploads name different parent folder IDs for the same path.

Evidence

14:05:47.499 [BoxAdapter] READ.list_delta.change: side='remote', change_type='create', raw_event_type='ITEM_UPLOAD',
             box_id='2528444531345', parent_id='427792947707', name='review_memo.md'
14:05:47.503 [LocalAdapter] READ.list_delta.change: side='local', change_type='create', item_type='file',
             name='review_memo.md', local_path='Work/HALVORSEN-MSA/run-1015-140500/review_memo.md', local_size=0
14:05:47.505 POST https://upload.box.com/api/2.0/files/content  {"name": "review_memo.md", "parent": {"id": "427791249458"}}
14:05:48.673 [BoxAdapter] CREATE.create_file: local_path='/mnt/box/Work/HALVORSEN-MSA/run-1015-140500/review_memo.md'
# from 14:05:53, a new conflict copy every 2-3 s:
review_memo.conflict.local.20261015T140553Z.md
review_memo.conflict.local.20261015T140556Z.md
review_memo.conflict.local.20261015T140558Z.md   ... 78 in total
Impact

A brief write collision becomes unbounded churn: the folder fills with copies, every mount downloads each one, and API usage climbs until someone intervenes.

Workaround

Exactly one writer sandbox per agent, so one agent's writes never land in two mounts.

Suggested fix

After writing a conflict copy, record the local version as resolved so the next cycle doesn't treat it as a new conflict. Rate-limit or cap conflict copies per path. When two mounts create the same new folder path at once, merge onto one Box folder rather than tracking two parents.

#5

Cannot reattach to existing sync state after a container restart

Medium
What happened

We kept ~/.box-mount in a persistent volume so a restarted container could resume. On restart, box-mount mount refused. mount.json still held the old daemon's PID, and in a new container that PID is often reused, frequently by the mount command itself.

Clearing bdlc.pid changed the message but still refused. The only path forward is unmount, which is a reset: it deletes sync.sqlite3 and the next mount re-downloads everything.

The reset also "preserves unsynced edits". In our case that resurrected a file whose Box copy had been trashed (the stuck file from finding 1), which then re-uploaded and synced back into every other sandbox.

Evidence
$ box-mount --data-path /home/boxsvc/.box-mount mount /mnt/box 427251217536
Mount already exists at /mnt/box.
/mnt/box | box_folder_id=427251217536 | pid=18 | status=stopped

# after removing data/bdlc.pid, or pointing the pid at a dead process
A previous mount existed at /mnt/box. Run 'box-mount unmount /mnt/box' before creating a new mount.

$ box-mount --data-path /home/boxsvc/.box-mount unmount /mnt/box
Reset: preserving unsynced edits and clearing synced entries in /mnt/box
Reset: deleting sync database at /home/boxsvc/.box-mount/data/sync.sqlite3
Unmounting /mnt/box ...
Unmounted /mnt/box.
Impact

Sandboxes are routinely restarted or rescheduled. Each restart costs a full re-download (finding 9), and the reset can bring back content that was deleted remotely.

Workaround

The container entrypoint runs unmount then mount whenever mount.json exists (about 8 seconds for our folder). For the crash demo we kill only the agent worker process, never the container running the daemon.

Suggested fix

Treat a recorded PID as live only if it is a running box-mount sync process (check its command line or a lock file), and otherwise resume from the existing sync database. A mount --resume option would also work. During a reset, drop local items whose Box copy is trashed rather than re-uploading them.

#6

Occasional missed remote-change notification

Medium
What happened

We timed six small-file transfers between two sandboxes. Five arrived in 3.7–4.7 seconds. In the sixth, the receiving daemon never got the change notification. The file arrived over two minutes later, only when the next transfer's notification triggered a delta listing that picked up both.

Evidence
# sender (sandbox-compliance)
13:14:53 [BoxAdapter] CREATE.create_file: local_path='/mnt/box/Work/_latency/compliance-to-extractor-5.txt'
# receiver (sandbox-extractor): nothing for #5 until #6's event arrives
13:17:01 [BoxAdapter] READ.list_delta.change: index=1, side='remote', change_type='create', raw_event_type='ITEM_UPLOAD' ...
13:17:01 [BoxAdapter] READ.list_delta.change: index=2, side='remote', change_type='create', raw_event_type='ITEM_UPLOAD' ...
13:17:02 [LocalAdapter] CREATE_OR_UPDATE.write_file: target='/mnt/box/Work/_latency/compliance-to-extractor-5.txt'
13:17:02 [LocalAdapter] CREATE_OR_UPDATE.write_file: target='/mnt/box/Work/_latency/compliance-to-extractor-6.txt'

# startup line on every daemon
ALF poller, local watch, retry scheduler, and remote poll (0s) running.
Workaround

A daemon re-lists remote changes about half a second after its own upload echoes back (skip_own_write_echo, then list_delta.complete). When an agent is waiting for a file that hasn't arrived, it writes a small "pulse" file to _sync/, which forces its own daemon to catch up.

Suggested fix

A periodic remote delta poll as a fallback (the log shows remote poll (0s); a configurable interval of 15 to 60 seconds would bound the delay). A box-mount sync --now command, safe to run beside the daemon, would also help.

#7

Downloaded files are made group read-only

Low
What happened

Following the guide's credential-isolation pattern (daemon user, agent user, shared group, setgid directory, default ACL), files the daemon downloads arrive as -rw-r--r--. That sets the ACL mask to r--, so the agent can read them but not update them. Folders the daemon creates are drwxr-sr-x.

Evidence
$ getfacl Work/_latency/compliance-to-extractor-4.txt
user::rw-
group::rwx              #effective:r--
group:boxmount:rwx      #effective:r--
mask::r--
$ su agent -c 'echo x >> Work/_latency/compliance-to-extractor-4.txt'
sh: 1: cannot create ...: Permission denied
Workaround

The entrypoint re-applies the group ACL to folders. Our filesystem layer falls back to write-then-rename when updating a downloaded file, which loses Box version history for that file (as the guide notes for atomic saves).

Suggested fix

Honour the parent directory's default ACL and the process umask when creating downloaded files, or offer a file-mode setting.

#8

No health or sync-state interface for the agent user

Low
What happened

With the daemon and agent separated as recommended, the agent cannot run box-mount status, because the state directory is private to the daemon user. Neither user can ask whether a particular local file has finished uploading, or whether a remote version has arrived.

Workaround

A root supervisor writes box-mount status output to a world-readable file every two seconds, and agents refuse to write while it is stale or not running. Handoffs compare content checksums and poll until the expected version is present.

Suggested fix

A read-only status file or socket readable by the mount's group, ideally with per-path sync state (pending upload, synced, conflict, error).

#9

Whole-folder download on every mount

Low
What happened

Each mount downloads the entire folder, and every new file syncs to every mount whether or not anything reads it. With five sandboxes the folder is downloaded five times at startup, and again on each restart (finding 5). We saw no on-demand or lazy option in the CLI or the guide.

Question

Is an on-demand mode planned, or a way to exclude subfolders from a mount? Until then, the guidance we'd suggest is to mount the narrowest folder each agent needs.

#10

High log volume at the default level

Low
What happened

The SDK logs full request and response bodies and event payloads as multi-line dumps at INFO. On a 10-file folder, each daemon wrote 12,900–15,500 lines (1.9–2.3 MB) of stderr.log in about 25 minutes. The same content is duplicated in per-run log files. Finding real errors means filtering through this.

Suggested fix

A log-level setting, and SDK network bodies at DEBUG. This also addresses finding 2.

#11

box-mount config crashes without an interactive terminal

Low
What happened

Running config with stdin closed loops on the prompt, then exits with an EOFError traceback. Environment variables work for non-interactive setup, so this matters mainly for automation that probes the CLI.

Evidence
Authentication type (oauth, jwt) [oauth]:
Configuring OAuth mode.
Client ID: Client ID is required.
...
  File "bdlc/auth_setup_cli.py", line 35, in _prompt_value
EOFError: EOF when reading a line
[PYI-13:ERROR] Failed to execute script 'cli' due to unhandled exception!
Suggested fix

Detect a non-TTY and exit with a message pointing to the BOX_* environment variables, or accept flags.

#12

Credential isolation on Docker Desktop for Mac

Docs
What happened

The guide recommends chmod 600 on the JWT file, owned by the daemon user. We first bind-mounted the JWT JSON from the Mac into the container. Inside the container it showed as -rw------- root, but the unprivileged agent user could still read it, because Docker Desktop's macOS file sharing does not enforce Linux permissions.

Workaround

The key is copied into each sandbox's Docker named volume (real ext4 permissions) before start, and never bind-mounted.

Suggested docs change

Note that file permissions only isolate credentials on a filesystem that enforces them, and recommend secrets stores or copying into the sandbox's own filesystem for Docker Desktop and similar setups.

What worked well

  • Good No FUSE and no privileged container. A plain directory meant ordinary file tools and our own filesystem layer worked unchanged.
  • Good Fast uploads (about 1.4 s) and typical cross-sandbox propagation of about 4 s.
  • Good Five daemons on one service account and one folder ran together without conflicts or rate-limit errors in our tests.
  • Good Own-write echo suppression (skip_own_write_echo) worked as expected, and gave us a reliable way to force a remote catch-up.
  • Good JWT setup through environment variables was simple, and status output is easy to parse.

Requests, in priority order

  1. Fix the inode-reuse binding and the root-folder fallback (finding 1).
  2. Redact tokens from logs (finding 2).
  3. Stop the conflict-copy loop (finding 3).
  4. Resume from existing sync state after a restart (finding 5).
  5. A fallback remote poll, or a safe sync-now command (finding 6).
  6. A group-readable status interface with per-path sync state (finding 8).
  7. File modes that respect default ACLs (finding 7), and a log-level setting (finding 10).
  8. Guidance on on-demand downloads or subfolder exclusion (finding 9).

How the demo uses Box Mount

Four agents process a vendor packet: an extractor, a compliance checker (two sandboxes, for failover), a contract reviewer and a coordinator. Each runs in its own Linux sandbox with its own box-mount daemon over the same Box folder. Temporal orchestrates them, and each agent's file operations run as Temporal activities inside its own sandbox.

Agents hand work to each other only through Box. The writer reports a checksum, and the reader waits until that exact version has synced into its own mount. This is why sync delays and misplaced files surfaced so clearly: every handoff checks that the file arrived intact. The checksums let Temporal wait out ordinary delays safely; findings 1 and 5 are the cases where waiting alone was not enough.
